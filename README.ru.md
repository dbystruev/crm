# Объекты и задачи

[English version](README.md)

Мини-CRM для строительства: менеджеры управляют портфелем объектов и проверяют
выполненную работу, а исполнители видят только назначенные им объекты и задачи,
проводят работу по полевым статусам и получают понятный комментарий, когда
задачу нужно доработать.

Живой деплой: [crm.bystruev.com](https://crm.bystruev.com)

Приложение работает в двух режимах:

- **Локальная демоверсия** — без настройки. Пример данных и вход живут в этом
  браузере, поэтому все экраны и сценарии можно попробовать сразу.
- **Живой Supabase** — аутентификация, общие данные, row-level security и
  правила процесса, обеспеченные на уровне базы данных.

## Возможности

- Вход по email и паролю с учётом ролей.
- Портфель менеджера: объекты, прогресс, открытые работы, просрочка и количество
  задач на проверке.
- Детальная страница объекта с фильтрами задач и очередью проверки.
- Отдельная страница задачи (`/:lang/tasks/:id`, например `/en/tasks/:id`):
  исполнитель, срок, описание, действия по роли и статусу и история статусов.
  Та же карточка задачи может открываться модальным окном из списков.
- Удаление объектов и задач только менеджером, с подтверждением.
- Обязательные комментарии при доработке и доступная только для чтения история
  статусов на всё время жизни задачи.
- Очередь **«Мои задачи»** для исполнителя с карточкой «следующая задача».
- Интерфейс на английском и русском с маршрутами по языку (`/en`, `/ru`).
- У демо-объектов и задач есть локализованные английские и русские названия,
  адреса и описания.
- Адаптивная вёрстка для компьютеров и мобильных устройств.
- Демо-данные сохраняются в `localStorage` после перезагрузки; режим Supabase
  общий для всех пользователей.

## Быстрый старт — локальная демоверсия

Требования: Node.js 20.19+ или 22.12+ (рекомендуется Node 22 LTS) и npm.

```bash
npm install
npm run dev
```

Откройте URL, который выведет Vite, и войдите под одним из демо-аккаунтов ниже.

Файл `.env` не нужен. Демо-бэкенд создаёт три объекта, тринадцать задач и
реалистичную историю прямо в браузере.

| Аккаунт | Email | Пароль |
| --- | --- | --- |
| Менеджер — Alex Morgan | `manager@bystruev.com` | `Crm2026!Manager` |
| Исполнитель 1 — Daniel Reyes | `worker1@hurated.com` | `Crm2026!Worker1` |
| Исполнитель 2 — Maya Chen | `worker2@buddian.com` | `Crm2026!Worker2` |

Форма входа по email и паролю также принимает эти демо-данные. Публичной
регистрации нет.

### Язык и маршрутизация

Приложение доступно на английском и русском. Язык является частью URL, а не
скрытой настройкой только на клиенте:

| URL | Язык |
| --- | --- |
| `/en` | Английский портфель |
| `/ru` | Русский портфель |
| `/en/objects/:id` | Детальная страница объекта на английском |
| `/ru/objects/:id` | Детальная страница объекта на русском |
| `/en/tasks/:id` | Детальная страница задачи на английском |
| `/ru/tasks/:id` | Детальная страница задачи на русском |
| `/ru/my-tasks` | Очередь исполнителя на русском |
| `/en/login` | Вход на английском |
| `/ru/login` | Вход на русском |

Открытие `/` перенаправляет на последний язык, сохранённый в этом браузере, затем
на язык браузера и затем на английский. Переключатель EN/RU в шапке сохраняет
текущую страницу, заменяя языковой префикс. Старые ссылки без префикса, например
`/objects/:id` или `/my-tasks`, автоматически перенаправляются на выбранный язык.

Все тексты интерфейса, бейджи статусов, кнопки, модальные окна, сообщения
валидации, уведомления и известные ошибки API/аутентификации переведены. Даты,
подписи сроков и приветствия используют активную локаль. Строки переводов лежат в
[`src/i18n/translations.ts`](src/i18n/translations.ts).

## Подключение живого проекта Supabase

### 1. Создайте проект

Создайте проект на [supabase.com](https://supabase.com). В разделе **Project
Settings → API** скопируйте URL проекта и **anon / publishable** ключ. Никогда не
используйте ключ `service_role` во фронтенде.

### 2. Запустите миграции

Откройте **SQL Editor** в Supabase и выполните файлы из
[`supabase/migrations/`](supabase/migrations/) в порядке номеров:

1. [`20260101_init.sql`](supabase/migrations/20260101_init.sql) — схема,
   триггеры, RLS и базовые гранты.
2. [`20260102_localized_content.sql`](supabase/migrations/20260102_localized_content.sql)
   — добавляет необязательные поля русского контента. Использует `add column if
   not exists`, поэтому безопасен и для новых проектов, и для обновлений.
3. [`20260103_manager_delete_permissions.sql`](supabase/migrations/20260103_manager_delete_permissions.sql)
   — DELETE-политики и гранты для объектов и задач, доступные только менеджерам.
4. [`20260104_disable_public_registration.sql`](supabase/migrations/20260104_disable_public_registration.sql)
   — триггер `prevent_public_signup` на `auth.users`.

Миграции создают:

- enum-типы `user_role` и `task_status`
- таблицы `profiles`, `objects`, `tasks` и `task_history`
- создание профиля для новых пользователей auth
- триггеры переходов статусов и аудита
- DELETE-политики для объектов и задач, доступные только менеджерам
- защиту от публичной регистрации на уровне базы данных
- индексы, политики row-level security и гранты API

Если вы используете Supabase CLI, выполните файлы через SQL Editor или обычный
процесс миграций. В репозитории нет `supabase/config.toml`, поэтому SQL Editor —
самый простой путь.

### 3. Необязательно: заполните демо-данными

Только для проекта разработки или staging выполните
[`supabase/seed.sql`](supabase/seed.sql). Он создаёт те же три аккаунта, что и
локальная демоверсия, три объекта, тринадцать задач и их историю. У демо-объектов
и задач есть русские поля `*_ru` рядом с английским контентом, и интерфейс
автоматически выбирает активный язык. У демо-аккаунтов доменные учётные данные из
таблицы выше. Повторный запуск seed также обновляет существующих пользователей
auth и email-идентификаторы на эти адреса и пароли.

> **Не запускайте seed на production.** Его учётные данные публично доступны в
> этом репозитории. Оставьте его для демо, preview и локальных экземпляров
> Supabase.

### 4. Добавьте переменные окружения

Скопируйте `.env.example` в `.env` и заполните значения проекта:

```bash
cp .env.example .env
```

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-or-publishable-key
```

Перезапустите dev-сервер после изменения переменных окружения.

### 5. Создайте реальных пользователей

Экрана регистрации нет. Создавайте коллег в **Authentication → Users** в
панели Supabase. Триггер базы данных создаёт профиль `worker` для каждого нового
пользователя auth.

Публичная регистрация также заблокирована на уровне базы данных миграцией
`supabase/migrations/20260104_disable_public_registration.sql`. Она устанавливает
триггер `prevent_public_signup` на `auth.users`, который отклоняет анонимные
API-регистрации. Дополнительно оставьте **Allow new users to sign up**
выключенным в настройках Supabase Auth как внешний барьер GoTrue. Политика на
уровне кода:

> Открытая регистрация отключена на уровне базы данных (триггер prevent_public_signup). Тестовых пользователей можно создать вручную в Supabase.

Приглашайте пользователей или создавайте аккаунты как администратор.

Чтобы назначить менеджера, выполните один раз в SQL Editor:

```sql
update public.profiles
set role = 'manager'
where id = (
  select id from auth.users where email = 'owner@company.com'
);
```

Только администратор с SQL/service-доступом может менять роли. API не может
повысить пользователя.

### 6. Запустите приложение

```bash
npm run dev
```

На странице входа должен появиться бейдж **Connected to Supabase**. Войдите под
реальным аккаунтом или одним из демо-аккаунтов из seed.

## Роли и процесс

### Менеджер

- Видит весь портфель и все задачи.
- Создаёт и редактирует объекты, задачи, исполнителей и сроки.
- Удаляет объекты и задачи. Удаление объекта также удаляет его задачи и их
  историю через каскадные внешние ключи.
- Принимает работу или запрашивает доработку, когда задача на проверке.
- Не может выполнять полевые переходы. Они принадлежат назначенному
  исполнителю.

### Исполнитель

- Видит только объекты, где у него есть хотя бы одна назначенная задача.
- Видит только свои задачи в карточках объектов и в **«Моих задачах»**.
- Начинает работу, отправляет её на проверку и возобновляет после доработки.
- Не может принимать работу, запрашивать доработку, редактировать содержимое
  задачи, удалять объекты или задачи, а также видеть объект или задачу другого
  исполнителя.

### Поток статусов

```text
new -> in_progress -> under_review -> accepted
                         |
                         +-> revision_requested -> in_progress
```

| Из | В | Кто | Правило |
| --- | --- | --- | --- |
| `new` | `in_progress` | Назначенный исполнитель | Начать работу |
| `in_progress` | `under_review` | Назначенный исполнитель | Отправить на проверку |
| `under_review` | `accepted` | Менеджер | Принять и закрыть |
| `under_review` | `revision_requested` | Менеджер | Нужен непустой комментарий |
| `revision_requested` | `in_progress` | Назначенный исполнитель | Возобновить работу |

`accepted` — терминальный статус. Недопустимые переходы (например,
`new -> accepted`) отклоняются триггером базы данных, даже если вызвать API
напрямую.

## Безопасность простыми словами

- **Аккаунты только по приглашению.** Экрана публичной регистрации нет, а
  анонимные регистрации отклоняются триггером `prevent_public_signup` на
  `auth.users` в `20260104_disable_public_registration.sql`. Администратор
  создаёт пользователей вручную в Supabase.
- **Исполнители видят только свою работу.** Политики базы данных ограничивают
  объекты и задачи назначениями вошедшего исполнителя. Скрытие кнопки — не
  защита; база данных применяет то же правило и к прямым вызовам API.
- **Процесс обеспечен на сервере.** Задача может двигаться только по разрешённым
  рёбрам статусов. Только назначенный исполнитель делает полевые переходы, и
  только менеджер принимает работу или запрашивает доработку.
- **Доработка требует объяснения.** Запрос доработки отклоняется без
  комментария. Комментарий сохраняется в истории задачи.
- **Историю нельзя редактировать через приложение.** У клиентов доступ только на
  чтение к `task_history`; записи аудита создают триггеры. Только менеджеры могут
  удалить задачу или объект, и такие удаления каскадно удаляют связанную историю
  вместе с записью.
- **Менеджеры назначаются осознанно.** Новые аккаунты всегда начинают как
  исполнители; смена роли требует доступа администратора, а не вызова API.
- **Публичный ключ Supabase — не пароль.** Он только идентифицирует проект.
  Данные защищают row-level security и триггеры. Никогда не кладите ключ
  `service_role` в Vite-приложение: все значения `VITE_*` попадают в бандл
  браузера.
- **Демо-учётные данные публичны.** Никогда не запускайте `supabase/seed.sql` на
  production.

Для реального запуска оставьте публичную регистрацию выключенной в Supabase Auth,
настройте подтверждение email, задайте Site URL и redirect URL для домена
деплоя и примените политику паролей, подходящую для вашей команды.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `profiles` | Одна строка на пользователя auth: отображаемое имя и роль `manager`/`worker` |
| `objects` | Строительные объекты; необязательные `name_ru`, `address_ru`, `description_ru` |
| `tasks` | Задачи, один исполнитель, один текущий статус; необязательные `title_ru`, `description_ru` |
| `task_history` | История статусов и комментарии только с добавлением записей |

`tasks.transition_comment` — временная колонка передачи комментария. Клиент
записывает комментарий вместе со сменой статуса; триггер базы данных копирует его
в `task_history` и очищает строку задачи. Так запись задачи остаётся чистой, а
полная история аудита сохраняется.

## Инструмент проверки

`verify.sh` разбирает markdown/plain-text спецификацию на требования и проверяет
их с помощью живых проверок работающего приложения, встроенных исполняемых
проверок и строгого семантического анализа кода через OpenRouter. По умолчанию он использует живое
приложение `https://crm.bystruev.com` и живой проект Supabase, а в заголовке
показывает хеш файла сборки и состояние API.

```bash
./verify.sh --list path/to/spec.md
./verify.sh -r 7 -y path/to/spec.md
./verify.sh --model nvidia/nemotron-3.5-lightning:free -y path/to/spec.md
```

Для семантических проверок нужен `OR_API_KEY` (или `~/.llm_config`). Живые проверки
используют демо-аккаунты из seed и публичный анонимный ключ, извлечённый из
задеплоенного бандла, если `SUPABASE_ANON_KEY` не задан.

## Деплой

```bash
npm run build
```

Разверните `dist/` на любом статическом хостинге. Приложение использует
клиентскую маршрутизацию, поэтому настройте резервный маршрут на `index.html`
для неизвестных путей:

- **Vercel:** `vercel.json` уже включён с rewrite.
- **Netlify:** `public/_redirects` включён и копируется в `dist/`.
- **Другие хостинги:** перенаправляйте все маршруты, кроме файлов, на `/index.html`.

Задайте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` в окружении сборки
хостинга. Vite встраивает эти значения во время сборки, поэтому после изменения
переменных нужен повторный деплой.

## Устранение неполадок

**«Неверный email или пароль» для демо-аккаунтов.** В живом проекте не выполнен
`supabase/seed.sql` или seed выполнен в другом проекте. Проверьте URL в
переменных окружения или используйте реальный аккаунт.

**«Не удалось загрузить профиль аккаунта».** Пользователь auth существует, но
его профиль отсутствует. Проверьте, что триггер `handle_new_user` из миграции
установлен, затем создайте профиль вручную или повторите шаг создания
пользователя.

**Исполнитель не видит объект.** Исполнители видят только объекты, где у них есть
назначенная задача. Сначала назначьте ему задачу на этом объекте. Это обеспечено
через RLS, а не только через интерфейс.

**Менеджер не может перевести задачу в «В работе».** Так задумано: полевые
переходы принадлежат назначенному исполнителю. Менеджеры проверяют работу после
её отправки на проверку.

**Изменения не синхронизируются в демо-режиме.** Демо-данные по задумке локальны
для одного браузера. Для общих данных подключите Supabase. Используйте сниппет
сброса выше, чтобы начать заново.
